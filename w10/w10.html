Likelihood and log-likelihood

So far we estimated with OLS, which needs a continuous outcome. Maximum likelihood works for any outcome we can give a distribution. It turns the usual question around:

Concept Formula What it says
Probability of the data fixed: how probable is it to observe the data if the parameter is ? A probability for discrete data, a density for continuous data. The ingredient of the likelihood
Likelihood Data fixed: how well does each explain them?
iid Independent, identically distributed observations: multiply
Log-likelihood Products become sums, the maximum stays where it is
Maximum likelihood estimate The under which the data are most likely

Evaluating the likelihood

The same likelihood function works for any three Binomial results, so we fix the data with a simple example. A coin of unknown bias is tossed times in each of three rounds, with 7, 9 and 8 heads. These are our data , , , and is given as well. Only , the probability of heads, is left open:

example_tosses <- 10
example_heads <- c(7, 9, 8)

We assume each round is a draw from the same Binomial distribution with . The objective: find the property of this distribution, here , that most plausibly produced these data.

Now we choose a value, say , and evaluate each factor. Written with a product sign, it is the same expression:

example_factors <- dbinom(example_heads, size = example_tosses, prob = 0.7)

The log-likelihood by hand

The likelihood of all flights, for any , is the product from above:

Taking the log turns the product into a sum:

binom_loglik <- function(p, k, n) {
  sum(log(choose(n, k)) + k * log(p) + (n - k) * log(1 - p))
}

The first term of the sum doesn’t contain at all. Leaving it out, as the lecture does, shifts the log-likelihood by a constant but keeps the maximum:

binom_loglik_short <- function(p, k, n) {
  sum(k * log(p) + (n - k) * log(1 - p))
}

A third version reuses binom_lik(). Taking the log of the product doesn’t help, since the product is already 0, and . Taking the log of each flight’s likelihood first, and then adding up, does:

binom_loglik_logged <- function(p, k, n) {
  sum(log(binom_lik(p, k, n)))
}

This works because a single flight’s likelihood is small, but not too small for R. At , where the likelihood gave 0, all three versions give a number. The full and the logged version agree, and the short one differs by the constant term:

Numerical optimization

A grid is only as fine as its steps. A numerical optimizer climbs “Mount Likelihood” directly. Before we start it, we write down what it searches over:

Parameter Defined on Bounds for the optimizer Starting value
, a probability lower = 0, upper = 1 0.5

Bounds. By default, an optimizer tries any real number. A below 0 or above 1 is not a probability, and or is then undefined, so the log-likelihood returns NaN. The bounds keep the search inside .

Starting value. The optimizer starts climbing at the starting value and follows the slope uphill from there. It must lie inside the bounds, and not on them: at or , the log-likelihood is and has no slope to follow. Without prior knowledge, 0.5, the middle of the range, is a neutral choice. A start close to the estimate saves steps, so a rough guess (e.g. from the grid) is even better.

Optimizer$new() sets up an optimizer object, here R’s nlminb(). $set_arguments() and $maximize() are functions that belong to this object, which is why they are called with a $. Everything after initial is passed on to the log-likelihood:

optimizer_bounded <- Optimizer$new(which = "stats::nlminb")
optimizer_bounded$set_arguments(lower = 0, upper = 1)

binom_mle <- optimizer_bounded$maximize(
  objective = binom_loglik,
  initial   = 0.5,
  k         = show_ups,
  n         = tickets_sold
)
p_hat <- binom_mle |>
  pluck("parameter")
p_hat
[1] 0.9097513

From the by-hand function to l() and ll()

We wrote out the log-likelihood once to see what it does. From now on, two short functions do this job for every model. l() returns each observation’s likelihood, using the distribution’s d...() function. With log = TRUE, the d...() function returns the log directly. ll() asks for that and adds the logs up. In short notation, the likelihood and its log are:

l <- function(p, k, n, log = FALSE) {
  dbinom(k, size = n, prob = p, log = log)
}

ll <- function(p, k, n) {
  sum(l(p, k, n, log = TRUE))
}

Why is there a sum() in ll(), but no prod() in l()? l() stands for one factor , not for the whole product . Given all flights, it returns one likelihood per flight:

ML and OLS

OLS can estimate this model too: lm(afd ~ 1) returns the sample mean as . So why use ML here? Because we know the answer. Before we use ML for models OLS can’t estimate (next week), we check it on one where the result is known.

With Normal errors, the result is exactly the same. Maximizing the Normal log-likelihood over means minimizing the sum of squared residuals, which is what OLS does. Both give the sample mean:

The optimizer only reaches it up to a small numerical tolerance. The estimate of differs slightly, as we will see.

Only the systematic component changes:

The linear part gets its own function, x_beta(). l() stays the same apart from calling it, and ll() doesn’t change at all. We will reuse this structure for every model from next week on. The likelihood and its log:

x_beta <- function(theta, x) {
  pluck(theta, 1) + pluck(theta, 2) * x
}

l <- function(theta, y, x, log = FALSE) {
  dnorm(y, mean = x_beta(theta, x), sd = exp(pluck(theta, 3)), log = log)
}

ll <- function(theta, y, x) {
  sum(l(theta, y, x, log = TRUE))
}

With Normal errors, maximizing the likelihood means minimizing the squared residuals, so the coefficients are the same. differs slightly: ML divides the RSS by , lm() by :

glance() reports lm()’s and the RSS (as deviance). Dividing by instead gives exactly the ML value:

turnout_model |>

  mutate(
    sigma_rss_n = sqrt(deviance / nobs),

lm()’s value is the right one here. The two estimated coefficients use up two degrees of freedom, and dividing by ignores that: on average, underestimates the error variance. With 399 counties, the difference is small.

For standard errors, ML uses the curvature of the log-likelihood at its peak, the Hessian: the steeper the peak, the more precise the estimate (see the lecture). Since these standard errors are built on , they come out slightly too small as well: ML underestimates the standard errors compared with OLS.

Concluding remarks

The likelihood asks which parameter value makes the observed data most likely. With iid data it is a product, and in practice a sum of logs, since products underflow. We wrote the log-likelihood out once. From now on, l() holds the distribution, x_beta() the linear part, and ll() adds up the logs. For the linear model, ML reproduces OLS. Next week, ML estimates a model that OLS can’t.
